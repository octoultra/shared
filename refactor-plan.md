## Порядок работы

### 1. Изучи кодовую базу

Прочитай сам, не полагаясь на догадки:

- конфиги: `package.json`, `tsconfig*.json`, `rsbuild.config.*`, конфиг ESLint, конфиг прокси/node-сервера, наличие OpenAPI-схемы или URL на неё;
- полное дерево `src/` и точку входа;
- роутер: как объявлены маршруты, есть ли data router, где хедер и как он скрывается на канвасе;
- HTTP-слой: чем делаются запросы (fetch, axios, ky), где базовый URL, как обрабатываются ошибки;
- использование TanStack Query: где `useQuery`/`useMutation`, как устроены query keys;
- сторы Zustand: какие есть, глобальные или на экземпляр, что в них хранится;
- канвас: как загружается JSON сценария, где живут nodes/edges, как сохраняется, где объявлены `nodeTypes`;
- панель свойств ноды и другие всплывающие панели: как открываются, как рендерятся динамические поля;
- списки сценариев, навыков, правил: где фильтры/поиск/сортировка, как они связаны с таблицей;
- стили: как подключена тема библиотеки, где переопределения React Flow, есть ли литералы цветов;
- тесты и скрипты проверки (`typecheck`, `lint`, `test`, `build`).

Для каждого вывода опирайся на конкретные файлы и строки.

### 2. Составь аудит

Таблица «требование спецификации → текущее состояние → разрыв → затронутые файлы». Пройди по всем разделам спецификации и по чеклисту «Соглашения и критерии соответствия». Отдельно выпиши риски (места с хрупкой логикой, отсутствие тестов, неявные связи) и открытые вопросы, на которые нельзя ответить по коду (например, отдаёт ли бэк OpenAPI, откуда приходит схема полей). Не додумывай ответы на открытые вопросы: помечай зависящие от них шаги как заблокированные.

### 3. Составь план из минимальных шагов

Главное требование: **после каждого шага приложение собирается, запускается и работает**, а пользователь может проверить это руками за несколько минут.

Правила нарезки шагов:

- Один шаг — одна причина изменения. Перенос файлов и изменение логики — всегда разные шаги.
- Ориентир — дифф до ~300 строк, не считая сгенерированного кода и чистых переносов.
- Используй strangler-подход: новое создаётся рядом со старым, потребители переключаются по одному, старое удаляется отдельным шагом.
- При переносе файлов оставляй временные реэкспорты со старых путей, если иначе придётся за один шаг править десятки импортов; удаление реэкспортов — отдельный шаг.
- Мигрируй сущности по одной: сначала одна страница списка целиком (например, навыки), затем остальные по образцу.
- Линтер границ включай сначала в режиме warn, переводи в error последним шагом, когда нарушений нет.
- Никаких шагов «заодно поправить»: всё, что не относится к целевой архитектуре, выноси в раздел «Вне плана».

Рекомендуемый порядок фаз (адаптируй под реальный код, пропускай то, что уже сделано):

0. Страховочная сетка: скрипты `typecheck`/`lint`/`build`, алиас `@/`, линтер границ в warn, при отсутствии тестов — минимальные smoke-проверки критичных потоков.
1. HTTP и API: инстанс ky и mutator, подключение orval и генерация рядом со старым слоем, перевод запросов на сгенерированные хуки по одному домену.
2. Маршрутизация: data router, `MainLayout` и `FullscreenLayout`, lazy-страницы.
3. Слоты хедера: `shared/layout-slots`, `RouteSlot`, перенос контролов списков в `handle`.
4. Списки: `shared/list` (`useListParams`, примитивы тулбара), перевод фильтров в URL — по одной сущности за шаг.
5. Канвас: стор черновика на экземпляр, доменная модель и мапперы, гидрация по смене `id`, сохранение через мутацию с `setQueryData`, реестр `nodeTypes`.
6. Панели: `shared/panels`, `PanelHost`, перевод инспектора, затем остальных панелей по одной.
7. Инспектор: реестр полей и `DynamicForm`, debounce записи в стор.
8. Стили: переопределения React Flow в одном файле, замена литералов на токены.
9. Финал: удаление старого кода и реэкспортов, линтер границ в error, сверка с чеклистом спецификации.

### 4. Формат каждого шага

```
### Шаг N.M — <короткое название>

Цель: зачем этот шаг и какой пункт спецификации он закрывает.
Зависит от: <номера шагов> | Заблокирован вопросом: <номер вопроса или «нет»>
Файлы:
- создать: <точные пути>
- изменить: <точные пути и что в них меняется>
- удалить: <точные пути>
Что сделать: пронумерованные действия, достаточно конкретные, чтобы их выполнил другой разработчик без доступа к этому чату. Сигнатуры новых функций и типов — явно.
Чего не делать: границы шага.
Проверка:
- автоматически: команды (`npm run typecheck`, `npm run lint`, `npm run build`, тесты) и ожидаемый результат;
- вручную: конкретные URL и действия в браузере и что должно произойти (например: «открыть /skills, ввести "abc" в поиск — URL стал ?search=abc, таблица отфильтрована, после F5 фильтр сохранился»).
Откат: как вернуть (обычно revert одного коммита) и что ещё учесть.
Риск: низкий/средний/высокий и почему.
```

## Структура итогового файла `docs/refactoring-plan.md`

1. Краткое резюме: текущее состояние в 3–5 предложениях, число фаз и шагов.
2. Аудит (таблица из пункта 2).
3. Риски.
4. Открытые вопросы — пронумерованные, с указанием блокируемых шагов.
5. План по фазам, шаги в формате выше.
6. Матрица покрытия: каждый пункт чеклиста спецификации → шаги, которые его закрывают. Пункт без шага — ошибка плана, исправь её.
7. Вне плана: найденные проблемы, не относящиеся к архитектуре.

Перед записью файла перепроверь план: каждый шаг оставляет приложение рабочим, нет шагов, совмещающих перенос и изменение логики, все пути файлов существуют в текущем коде или явно создаются, порядок зависимостей не нарушен. После записи выведи в чат только резюме и список открытых вопросов.
