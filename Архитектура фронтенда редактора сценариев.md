## Назначение и принципы

Документ фиксирует архитектурные договорённости фронтенда: слои, направления зависимостей, способы хранения состояния и механизмы расширения. Он не описывает предметную область: конкретные сущности, экраны и бизнес-правила живут в коде модулей и в их собственной документации.

Архитектура — вертикальные модули поверх тонкого общего ядра. От FSD взяты однонаправленные зависимости и группировка по фичам, от clean architecture — изоляция API-контракта от модели UI. Дробление на много слоёв и обязательные сегменты внутри модулей не используются.

Принципы:

- **Жёстких границ три:** API-контракт, доменная модель (там, где она есть) и направление импортов. Внутри модуля файлы раскладываются свободно.
- **У каждого вида состояния один владелец.** Серверное — TanStack Query, редактируемое и UI-состояние — Zustand, параметры экранов — URL. Данные не дублируются без явной причины.
- **Расширение через реестры, а не условия.** Ядро предоставляет механизм, модули регистрируют в нём свои реализации.
- **Абстракции по необходимости.** Доменная модель и мапперы появляются только там, где модель бэкенда и модель UI действительно расходятся. В остальных местах используются сгенерированные типы API напрямую.
- **Страница — композиция, а не логика.** Логика и запросы живут в модулях.

## Стек и инфраструктура

| Задача | Инструмент | Договорённость |
| --- | --- | --- |
| UI | React | функциональные компоненты и хуки |
| Маршрутизация | react-router | только data router: `createBrowserRouter` + `RouterProvider` |
| Сборка, dev-сервер | rsbuild | прокси `/api` через `server.proxy` |
| Серверное состояние | TanStack Query | единственный кэш данных бэкенда |
| Клиентское состояние | Zustand | черновики, UI-состояние, сервисы |
| Графовые редакторы | React Flow | controlled-режим, данные из стора |
| HTTP | ky | единственный инстанс в `api/http.ts` |
| Кодоген API | orval | типы и хуки TanStack Query из OpenAPI |
| Валидация | zod | схемы URL-параметров и внешних данных |
| UI-компоненты | внутренняя библиотека | обёртки только с добавленным поведением |
| Стили | css-in-js | только токены темы |

**Сеть.** Приложение всегда обращается к относительному префиксу `/api`; базовый URL не переключается через env. В dev запросы проксирует rsbuild, в проде — node-сервер, который отдаёт статику и проксирует тот же префикс.

**Ретраи.** В ky `retry: 0`; повторами управляет только TanStack Query, иначе попытки перемножаются.

## Слои и правила зависимостей

```
src/
├── app/            # сборка приложения: провайдеры, роутер, layouts
├── pages/          # страницы: композиция модулей, handle маршрута
├── modules/        # вертикальные фичи
│   └── <module>/
│       ├── ...     # внутренняя раскладка — на усмотрение модуля
│       └── index.ts# публичный API модуля
├── domain/         # доменные модели и мапперы, без React (по необходимости)
├── api/
│   ├── generated/  # результат кодогена, руками не редактируется
│   ├── http.ts     # инстанс HTTP-клиента
│   └── mutator.ts  # адаптер кодогена к HTTP-клиенту
└── shared/         # инфраструктура без знания о предметной области
    ├── ui/         # обёртки над библиотекой компонентов
    ├── layout-slots/
    ├── list/       # механика списочных экранов
    ├── panels/     # сервис панелей
    ├── hooks/
    └── styles/
```

| Слой | Отвечает за | Может импортировать |
| --- | --- | --- |
| `app` | провайдеры, роутер, layouts | всё |
| `pages` | композицию модулей на маршруте, слоты | `modules`, `shared` |
| `modules` | фичи: UI, локальные сторы, работу с данными | `domain`, `api`, `shared`, публичный API других модулей по правилу ниже |
| `domain` | модели и преобразования данных | `api/generated` (только типы), `shared` |
| `api` | контракт и транспорт | `shared` |
| `shared` | предметно-независимую инфраструктуру | только `shared` |

Правила:

- Импорт против направления таблицы запрещён.
- Снаружи модуль доступен только через `index.ts`; глубокие импорты запрещены.
- Модули по умолчанию не зависят друг от друга. Если модуль предоставляет общий контекст для других (например, стор редактора, которым пользуются панели), это явно оформляется в его публичном API, а зависимость — односторонняя, без циклов.
- `shared` не знает о предметной области: в нём нет имён сущностей и обращений к API.
- Алиас `@/` указывает на `src/`.
- Границы проверяет линтер (`eslint-plugin-boundaries` или `import/no-restricted-paths`).

## Маршрутизация и layouts

Различия в обрамлении страниц выражаются ветками роутера с разными layout-маршрутами, а не условиями внутри общих компонентов. Компонент обрамления (хедер, сайдбар) не проверяет, на какой он странице.

```tsx
// app/router.tsx — схема
createBrowserRouter([
  {
    element: <MainLayout />,          // обрамление с хедером
    errorElement: <RouteError />,
    children: [
      { path: '<route>', lazy: () => import('@/pages/<page>') },
    ],
  },
  {
    element: <FullscreenLayout />,    // без обрамления
    errorElement: <RouteError />,
    children: [
      { path: '<route>/:id', lazy: () => import('@/pages/<page>') },
    ],
  },
]);
```

Правила:

- Каждая страница — lazy-модуль, экспортирующий `Component` и при необходимости `handle`.
- Новый вид обрамления — новый layout-маршрут, а не флаг в существующем.
- Ошибки маршрутов обрабатываются `errorElement` на уровне layout.
- Страница не делает запросов и не содержит бизнес-логики: она компонует модули и объявляет слоты.

## Слоты layout

Layout только размечает места под контент компонентами `<RouteSlot name="…" />`; что попадёт в слот, объявляет маршрут через `handle`. Layout не знает ни о страницах, ни о наличии контента.

```ts
// shared/layout-slots/types.ts
export type SlotName = 'toolbar' | 'actions';  // закрытый список имён
export type AppRouteHandle = { slots?: Partial<Record<SlotName, ComponentType>> };
export const isAppHandle = (h: unknown): h is AppRouteHandle =>
  typeof h === 'object' && h !== null && 'slots' in h;
```

```tsx
// shared/layout-slots/RouteSlot.tsx
export const RouteSlot = ({ name, fallback = null }: { name: SlotName; fallback?: ReactNode }) => {
  const matches = useMatches();
  const SlotComponent = matches
    .map((m) => (isAppHandle(m.handle) ? m.handle.slots?.[name] : undefined))
    .findLast(Boolean);
  return SlotComponent ? <SlotComponent /> : fallback;
};

// в layout
<RouteSlot name="toolbar" />

// на странице
export const handle: AppRouteHandle = { slots: { toolbar: <Module>Toolbar } };
```

Правила:

- Имена слотов — закрытый union `SlotName`; новый слот = имя в union + `<RouteSlot>` в разметке layout.
- `findLast` даёт наследование: дочерний маршрут без слота показывает слот ближайшего родителя.
- Компонент слота не получает пропсов от страницы. Связь со страницей — через URL, стор модуля или кэш запросов.
- Слот рендерится в дереве layout и не видит провайдеров, поставленных внутри страницы; общие провайдеры живут в `app/` или в layout.

## Слой API

Типы, запросы и хуки TanStack Query генерируются orval из OpenAPI-схемы бэкенда; все HTTP-вызовы проходят через единственный инстанс ky.

```ts
// orval.config.ts
export default defineConfig({
  api: {
    input: '<путь или URL OpenAPI-схемы>',
    output: {
      target: 'src/api/generated',
      client: 'react-query',
      mode: 'tags-split',
      override: {
        mutator: { path: 'src/api/mutator.ts', name: 'apiRequest' },
        query: { signal: true },
      },
    },
  },
});
```

```ts
// api/http.ts
export const http = ky.create({ prefixUrl: '/api', retry: 0, hooks: { /* нормализация ошибок */ } });

// api/mutator.ts
export const apiRequest = <T>({ url, method, params, data, signal }: RequestConfig) =>
  http(url.replace(/^\//, ''), { method, searchParams: params, json: data, signal }).json<T>();
```

Правила:

- `api/generated` не редактируется руками. Регенерация — скрипт `gen:api`; результат коммитится, CI проверяет актуальность.
- Сгенерированные типы — это DTO. Там, где UI отображает данные как есть, они используются напрямую.
- Query keys берутся только из сгенерированных `get…QueryKey()`; захардкоженные ключи запрещены.
- Ошибки нормализуются в хуке ky в единый тип `ApiError`; решение, как их показать, принимает модуль.
- Эндпоинты, которых нет в схеме, допускаются как исключение в `api/manual/` поверх того же инстанса `http`.
- Прямые `fetch`, axios и другие клиенты запрещены.

## Виды состояния

У каждого вида состояния один владелец. Перед тем как завести новое состояние, определите его вид по таблице.

| Вид | Пример | Владелец | Время жизни |
| --- | --- | --- | --- |
| Серверное | данные, полученные с бэкенда | TanStack Query | кэш запросов |
| Параметры экрана | поиск, фильтры, сортировка, пагинация, открытая вкладка | URL search params | адрес страницы |
| Черновик | редактируемая копия серверных данных | Zustand-стор на экземпляр экрана | пока открыт экран |
| UI-сервис | открытые панели, уведомления | Zustand-стор в `shared` | сессия или экран |
| Эфемерное модуля | выбранные строки, раскрытые узлы | Zustand-стор модуля или `useState` | пока смонтирован модуль |
| Локальное компонента | значение инпута до debounce, hover | `useState` | пока смонтирован компонент |

Правила:

- Серверные данные не копируются в Zustand ради удобства доступа. Копия допустима только как черновик (раздел «Редактируемые данные»).
- Состояние, которым можно поделиться ссылкой или которое должно пережить перезагрузку, живёт в URL.
- Сторы, привязанные к экрану, создаются на экземпляр (`createStore` + провайдер) и умирают вместе с экраном. Глобальные синглтон-сторы допустимы только для сервисов в `shared`.
- Подписка на стор — всегда через узкий селектор; объекты и массивы — с `useShallow`.

## Списочные экраны

Параметры списка (поиск, фильтры, сортировка, пагинация) живут в URL. Контролы пишут в URL, список читает из URL и передаёт параметры в сгенерированный хук; смена параметров меняет query key и запускает запрос. Контролы и список не передают друг другу пропсы — поэтому контролы можно размещать где угодно, в том числе в слоте layout.

```ts
// modules/<module>/params.ts
const paramsSchema = z.object({
  search: z.string().default(''),
  sort: z.enum([/* поля сортировки */]).default(/* … */),
  page: z.coerce.number().default(1),
});
export const use<Module>Params = () => useListParams(paramsSchema);

// контрол — пишет
const [params, setParams] = use<Module>Params();
setParams({ search, page: 1 }, { replace: true });

// список — читает
const [params] = use<Module>Params();
const query = useGet<Entities>(params, { query: { placeholderData: keepPreviousData } });
```

`shared/list` предоставляет:

- `useListParams(schema)` — обёртку над `useSearchParams`: парсинг через zod с дефолтами, невалидные значения не ломают экран, значения по умолчанию не пишутся в URL;
- предметно-независимые контролы: поиск с локальным состоянием и debounce (\~300 мс), выбор сортировки, фильтры-чипы.

Правила:

- Схема параметров одна на экран и лежит в модуле; контролы и список используют один и тот же хук.
- Текстовый поиск пишется с `replace: true`, дискретные фильтры и сортировка — push, чтобы работала кнопка «назад».
- Любая смена фильтра сбрасывает страницу на первую.
- Запрос делает компонент модуля, не страница.

## Редактируемые данные: снимок и черновик

Когда пользователь долго редактирует сложный объект (граф, форму со многими полями) и сохраняет изменения явно или автосейвом, данные существуют в двух видах: снимок — последняя сохранённая версия в кэше TanStack Query, черновик — рабочая копия в Zustand-сторе экрана. Компоненты редактора читают и пишут только черновик.

Поток данных:

1. Экран загружает снимок сгенерированным хуком.
2. При открытии объекта (смене его идентификатора) стор черновика гидрируется из снимка; при необходимости через мапперы в модель UI.
3. Изменения пишутся только в черновик; стор ведёт флаг `isDirty`.
4. Сохранение берёт черновик, преобразует обратно в DTO и отправляет мутацию.
5. После успеха ответ сервера кладётся в кэш через `setQueryData`, флаг `isDirty` сбрасывается; стор не пересоздаётся.

Правила:

- Гидрация — только при смене идентификатора объекта, не на каждое обновление данных запроса; иначе рефетч затрёт черновик.
- Для запроса снимка на экране редактора отключается `refetchOnWindowFocus`.
- Стор черновика создаётся на экземпляр экрана и отдаётся провайдером.
- Если модели бэкенда и UI расходятся, преобразования живут в `domain/mappers` как чистые функции; DTO не проникают в компоненты редактора.
- Уход с экрана при `isDirty` блокируется подтверждением (`useBlocker`).
- Undo/redo при необходимости — `zundo` поверх стора черновика.

Для графовых редакторов на React Flow дополнительно:

- React Flow работает в controlled-режиме: `nodes`, `edges` и обработчики изменений берутся из стора черновика.
- `nodeTypes` и `edgeTypes` объявляются вне компонентов, через реестр.
- Кастомные ноды обёрнуты в `memo` и подписываются на свои данные по идентификатору.

## Реестры и формы по схеме

Если набор вариантов растёт (типы нод графа, типы полей, панели), ядро предоставляет реестр «ключ → реализация», а не switch по типам. Добавление варианта — новая реализация и одна регистрация, без правок ядра.

```ts
// общий вид реестра
const registry: Record<Key, Implementation> = { /* key: Implementation */ };

// использование с безопасным фолбэком
const Impl = registry[key] ?? Fallback;
```

Формы, описание которых приходит с бэкенда, строятся по этому же принципу:

```ts
type FieldComponent = ComponentType<{
  field: FieldSchema;              // описание поля из схемы
  value: unknown;
  onChange: (value: unknown) => void;
}>;

const fieldRegistry: Record<FieldType, FieldComponent> = { /* тип поля → компонент */ };
```

Правила:

- Неизвестный ключ не роняет экран: используется фолбэк-реализация с понятным сообщением.
- `DynamicForm` проходит по схеме и берёт компонент поля из реестра; сам он не знает о типах полей.
- Значения формы держатся локально и пишутся в стор-владелец с debounce (\~300 мс), чтобы ввод не перерисовывал весь экран.
- Схемы, которые меняются редко, кэшируются с `staleTime: Infinity`.
- Валидация описывается в схеме; при необходимости из неё собирается zod-схема.

## Сервис панелей

Всплывающие панели управляются сервисом в `shared/panels`, который ничего не знает о предметной области. Модули регистрируют свои панели сами; типы props проверяются через module augmentation.

```ts
// shared/panels/types.ts
export interface PanelRegistry {}   // расширяется модулями

// modules/<module>/panel.ts
declare module '@/shared/panels' {
  interface PanelRegistry {
    '<panel-key>': { /* props панели */ };
  }
}
registerPanel('<panel-key>', lazy(() => import('./<Panel>')));

// открытие из любого места
panels.open('<panel-key>', { /* props, проверяются TS */ });
```

Устройство:

- Zustand-стор со стеком `{ key, props }[]` и методами `open`, `close`, `replace`, `closeAll`.
- `registerPanel(key, component)` — реестр компонентов.
- `<PanelHost />` рендерит панели в общей обёртке (анимация, Esc, кнопка закрытия, ресайз). Хост ставится там, где панели должны появляться; при его размонтировании стек очищается.

Политики:

- Повторный `open` с тем же ключом заменяет props, а не создаёт копию.
- Панель может зарегистрировать `beforeClose` для подтверждения закрытия.
- В props передаются идентификаторы, а не данные; панель читает данные селекторами и закрывается сама, если они исчезли.
- Выделение в UI и открытая панель — разные состояния: выделение не открывает панель неявно.

## Стилизация

Стили пишутся на css-in-js и используют только токены темы внутренней библиотеки; литералы цветов, размеров и отступов в компонентах запрещены.

- `ThemeProvider` библиотеки подключается в `app/providers.tsx`.
- Глобальные переопределения сторонних библиотек (например, классов React Flow) собраны в отдельных файлах в `shared/styles`, по файлу на библиотеку.
- Стили компонента живут рядом с ним; общие — в `shared/styles`.
- Обёртки в `shared/ui` создаются только ради добавленного поведения или композиции. Прямой импорт компонентов библиотеки разрешён везде.

## Соглашения и критерии соответствия

Код соответствует архитектуре, когда выполнены все пункты ниже; их проверяют ревью и, где возможно, линтер.

- [ ] Структура `src/` соответствует разделу «Слои и правила зависимостей».
- [ ] Линтер границ включён в режиме error, нарушений нет.
- [ ] Модули доступны снаружи только через `index.ts`, циклических зависимостей нет.
- [ ] В `shared` нет имён предметной области и обращений к API.
- [ ] Используется data router; различия обрамления выражены layout-маршрутами; страницы — lazy-модули.
- [ ] Layout-компоненты используют `RouteSlot` и не содержат условий по маршрутам.
- [ ] Все HTTP-вызовы идут через `api/http.ts`; прямых `fetch` и других клиентов нет.
- [ ] Запросы к бэкенду — из `api/generated`; query keys — из `get…QueryKey()`.
- [ ] Каждый вид состояния хранится у владельца из раздела «Виды состояния».
- [ ] Параметры списочных экранов — в URL через `useListParams`.
- [ ] Редакторы работают по схеме «снимок и черновик»; компоненты редактора не вызывают `useQuery`.
- [ ] Расширяемые наборы вариантов подключены через реестры с фолбэком.
- [ ] Панели открываются только через сервис панелей.
- [ ] Цвета, размеры и отступы — из токенов темы.

Именование:

- папки и не-компонентные файлы — kebab-case, компоненты — PascalCase;
- хуки — `useXxx`, сторы — `xxxStore` и `useXxxStore`;
- публичный API модуля экспортирует только то, что используется снаружи.
